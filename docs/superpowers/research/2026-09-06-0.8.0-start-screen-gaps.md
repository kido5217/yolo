# 0.8.0 Start-Screen Gap Inventory

Wayfinder research for the 0.8.0 start screen. Answers the ten questions on
`yolo-dhf.1` against the current tree (HEAD `bcc5ced`, tag base `v0.7.0`) and
the opencode v1.18.18 reference clone at `/tmp/opencode-upstream`. Yolo paths
are repo-relative; upstream paths are under `/tmp/opencode-upstream/`. Every
claim carries a `file:line` citation.

## Q1. What does the home prompt submit do today (type + enter on home)?

**Finding: it does NOT send the typed text.** Enter on the home route is
intercepted before the prompt's own send path and only creates a new session;
the typed text is left in the prompt input, unsent and uncleared.

- The key ladder tries the route handler before the prompt fallback:
  `handleKey` → `handleHomeKey` on the home route, only falling through to
  `handlePromptKey` (the send path) if the route handler returns
  "not handled" — `internal/tui/keys.go:48-56`.
- On home, Enter is bound to `homeKeyMap.Enter` and dispatched to
  `homeEnter()` — `internal/tui/home.go:42` (binding), `home.go:357-359`
  (dispatch), `home.go:370-381` (`homeEnter`).
- `homeEnter` at cursor 0 (the "New session" row, the default position)
  returns only `createSessionCmd()`; at a session row it opens that session.
  It never reads `a.prompt.input` — `internal/tui/home.go:371-380`.
- `createSessionCmd` POSTs `/session` with an empty title —
  `internal/tui/hydrate.go:136-143`, `internal/tui/client/client.go:142-146`.
  The server fills defaults: title→"New session", model→provider default,
  agent→storage column default "build" — `internal/server/handlers_session.go:98-116`,
  `internal/storage/migrate.go:23`.
- `applySessionCreated` puts the session first and navigates, again with no
  prompt interaction — `internal/tui/hydrate.go:145-153`.
- The prompt's real send path (`handlePromptKey` → `promptEnter`) is only
  reached when the route handler declines the key — `internal/tui/keys.go:56`,
  `internal/tui/keys.go:241`. So on home the typed text is neither submitted
  nor cleared; it persists into the session route.
- Contrast upstream: the home prompt submit sends the typed text as the
  session's first message, passing the current agent + model —
  `/tmp/opencode-upstream/packages/tui/src/component/prompt/index.tsx:961-1004`.

## Q2. Agent cycling (tab/shift+tab), the agent list source, and the current-agent source

**Finding: the `tab`/`shift+tab` bindings are defined but never wired —
agent cycling is effectively absent.** The agent list and current agent are
both available.

- Bindings exist in the registry: `agent_cycle`=`tab`,
  `agent_cycle_reverse`=`shift+tab`, with command names `agent.cycle` /
  `agent.cycle.reverse` — `internal/tui/keymap.go:135-136`,
  `internal/tui/keymap.go:332-333`.
- But `agent_cycle` is in **no active context group**: `contextGroups[BaseMode]`
  lists `command_list, app_exit, model_list, agent_list, status_view,
  theme_list, session_new, session_list, tips_toggle, sidebar_toggle` (no
  `agent_cycle`), and the `session` group is only
  `messages_page_up, messages_page_down, session_interrupt, session_rename` —
  `internal/tui/keymap.go:816-823`.
- And `dispatchCommand` has **no case** for `agent_cycle` (cases are
  `command_list, app_exit, model_list, agent_list, status_view, theme_list,
  session_new, session_list, provider_connect, tips_toggle, sidebar_toggle,
  help_show`) — `internal/tui/keys.go:132-173`. So `tab` falls through to the
  prompt input and does nothing to agents.
- Agent list source: `store.Agents` (`internal/tui/store/store.go:20`) filled
  by `ListAgents` → `GET /agent` — `internal/tui/client/client.go:266`,
  `internal/server/server.go:112`. The server serves the built-ins
  `build`/`plan`/`yolo` plus custom agents — `internal/server/handlers_catalog.go:11-15`.
  The dialog flattens them (title=name, value=name) — `internal/tui/dialog.go:907-917`.
- Current agent source: `store.Current.Agent` on the session route, else
  `store.Config["agent"]` — `currentAgentName`, `internal/tui/dialog.go:892-900`;
  wire fields `internal/protocol/session.go:30`, `internal/protocol/config.go:39`.
- The reachable agent picker is `agent_list`=`<leader>a` → `openAgentDialog`
  — `internal/tui/keymap.go:134`, `internal/tui/keys.go:140-141`,
  `internal/tui/dialog.go:879`. Applying uses `patchDlgCmd("agent", name,
  thisSession)` → `PATCH /session/{id}` or `PATCH /config` —
  `internal/tui/dialog.go:974-976`.
- Display name for a meta line: upstream renders
  `Locale.titlecase(agent().name)` (`/tmp/opencode-upstream/.../prompt/index.tsx:1450`);
  yolo already has the `titlecase` port (`internal/tui/locale.go:47`) and the
  agent names are lowercase (`build`/`plan`/`yolo`).
- Upstream default keys match yolo's registry values: `tab` / `shift+tab` —
  `/tmp/opencode-upstream/packages/tui/src/config/keybind.ts:130-131`.

## Q4. Permission mode (auto/ask) display

**Finding: absent.** yolo has per-tool-call allow/deny/ask rules but no
user-facing auto/normal "permission mode" to display.

- yolo's permission engine is rule-based: actions `allow`/`deny`/`ask`
  (`RuleAllow`/`RuleDeny`/`RuleAsk`) with an `Evaluate` —
  `internal/permission/permission.go:25-27`, `:35`. These gate individual
  tool calls; there is no global mode state.
- The closest analog is the `yolo` built-in agent ("Permits everything without
  prompts", a permissive rule matrix) — `internal/server/handlers_catalog.go:14`,
  `internal/permission/builtins.go`. But that is an agent, not a toggle.
- Upstream has the concept yolo lacks: `PermissionMode = "auto" | "normal"`,
  seeded from `args.auto` — `/tmp/opencode-upstream/.../context/permission.tsx:5`,
  `:11-12` — and the home meta line shows `auto` when the mode is `auto` —
  `/tmp/opencode-upstream/.../prompt/index.tsx:1452`.

## Q5. Shell mode / "Run a command..." placeholder

**Finding: absent.** yolo's prompt is a single-line input with no mode and no
placeholder.

- The prompt model is a bare single-line `textinput` with no "shell"/"normal"
  mode — `internal/tui/prompt.go:19-23`.
- `NewApp` builds a plain `textinput` with no `Placeholder` set —
  `internal/tui/app.go:181-189`.
- Upstream's shell mode is a distinct state toggled by `!` at the input, with
  a `Run a command... "<example>"` placeholder, an `Ask anything...` normal
  placeholder, and a `session.shell` submit —
  `/tmp/opencode-upstream/.../prompt/index.tsx:830-837` (toggle),
  `:1314-1319` (placeholders), `:1061-1070` (`session.shell`).

## Q9. Does the home route render the always-on model footer, and is it visible?

**Finding: the code renders it on home, but it is NOT visible in the
screenshot.** The home route has no viewport height budget, so a long session
list pushes the trailing prompt + footer lines below the visible bottom edge.

- `view()` unconditionally appends the prompt line and the status footer after
  the route block on both routes — `internal/tui/view.go:54` (prompt),
  `internal/tui/view.go:76` (footer).
- `footerView` has an explicit `routeHome` branch rendering
  `model · agent · ↑in ↓out · ● live` from `store.Config` —
  `internal/tui/footer.go:64-75`.
- This home footer string is unit-pinned: "home uses config defaults" →
  `"kido/q · build · ↑0 ↓0 · ● live"` — `internal/tui/footer_test.go:87-91`.
- In `yolo_start_screen.png` the last visible line is the home destination
  line (`~/network/projects/yolo · Show keyboard shortcuts with ctrl+x`, the
  `homeFooterLine`); below it the terminal is empty — no prompt line, no
  status footer.
- Why: unlike the session route, which subtracts a line for the prompt and a
  line for the footer from the viewport so the frame fits the terminal —
  `internal/tui/view.go:113` — the home route renders an unbounded session
  list (`renderClamped(..., -1)`, capped only by `maxHomeSessions = 50`) —
  `internal/tui/home.go:113`, `internal/tui/home.go:51`,
  `internal/tui/home.go:125-130`. With ~33 sessions, the home block alone
  (4-line logo + "New session" + 33 rows + divider + help + tip + destination)
  fills the terminal height, so the prompt and status-footer lines that
  `view()` appends after it fall below the visible bottom.
- Note the bubbletea v2 renderer drops the *top* lines when a frame exceeds
  the terminal (`/home/kido/go/pkg/mod/charm.land/bubbletea/v2@v2.0.9/cursed_renderer.go:349-350`),
  so the observed "top intact, bottom missing" is a frame that fits the
  terminal with its trailing lines at/below the last row — not top-clipping.

## Q10. Version injection

**Finding: `main.version` is a `git describe` string, not plain semver; the
TUI never receives it today.**

- The version var defaults to `"0.0.0-dev"` and is set at build via ldflags —
  `cmd/yolo/main.go:36`, `cmd/yolo/main.go:41-42`.
- The build injects `git describe --tags --always --dirty` — `justfile:1`,
  `justfile:3-4`. With the latest tag `v0.7.0` and 8 commits ahead, the
  current value is `v0.7.0-8-gbcc5ced` (verified via `git describe`).
- That is not plain semver: it carries a leading `v`, a `-N-g<sha>` distance
  suffix, and a possible `-dirty` suffix. A plain-semver home-footer version
  would need to strip the leading `v` and the `-[0-9]+-g[0-9a-f]+(-dirty)?`
  tail (at a clean tagged commit, `git describe` yields just `v0.8.0`).
- The TUI does not receive the version: `NewApp` takes
  `(client, store.State, startSessionID, theme.Engine)` with no version arg —
  `internal/tui/app.go:151`, called at `cmd/yolo/main.go:742-747` — and no
  `/version` wire endpoint exists. So surfacing a version on the home footer
  requires injecting `main.version` into the TUI (or a new wire field).
