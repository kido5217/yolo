# golang-error-handling — session+llm+provider+permission
Date: 2026-08-20 · chunk: session+llm+provider+permission · source files: 25

## Findings

- [error-1] P1 internal/permission/service.go:276 — `resolve()` early-returns when `db.ReplyPermission` fails with any error other than `storage.ErrNotFound`, skipping BOTH the `permission.replied` publish (:283) and `deliver(e, d)` (:287). The pending entry was already deleted from the map (:269), so the engine's blocked `Ask` (service.go:176-182 `select` on `entry.ch` / `ctx.Done()`) is never unblocked: a transient DB error (lock, I/O) during a Reply/hang-resolve hangs the turn indefinitely until the user Aborts or the process shuts down, and the DB row is left response=NULL while in-memory state says resolved (inconsistent). Contrast the persist-failure path in `Ask` (:165-173), which correctly delivers Deny and returns the error. — fix: persist is best-effort here — deliver the decision and publish regardless of the DB result; keep the `ErrNotFound` tolerance, log or wrap the other DB errors (a logger seam or a returned-from-`resolve`/`Reply` error). — contract-risk: none
- [error-2] P2 internal/session/engine.go:334 — when the per-turn `loadCfg` fails (`cfgErr != nil`), `e.perm.SetConfigRules` is never called, so `permission.Service` keeps the PREVIOUS turn's config rules in `cfgRules` while `rulesetForRow` (policy.go:46-52) degrades to "no config rules" as documented (deviation 24c; engine.go:338-339 comment says the same). Same turn, two rulesets: e.g. a config `{doom_loop: allow}` that was loaded on turn N still auto-allows doom-loop asks on turn N+1 after the config file breaks, instead of degrading to ask. Contradicts the code's own documented per-turn config-load tolerance. — fix: call `e.perm.SetConfigRules(cfgRules)` unconditionally after the `cfgErr == nil` block (i.e. also set empty rules on load failure). — contract-risk: none
- [error-3] P2 internal/permission/service.go:80 — `EvaluateRules` (:80-82) and `decisionFor` (:100-103) swallow the `LoadBuiltins` "unknown agent" error and fall back to an EMPTY builtin set, while `Engine.rulesetForRow` (policy.go:35-43) falls back to the "build" matrix for the same condition (its comment: "unknown (custom) agent: fall back to the build matrix (v1 custom-agent behavior)"). With a config-defined custom agent (reachable: `protocol.Config.Agents`), tool visibility is evaluated with the build matrix but decisions are evaluated with no builtins at all — e.g. `plan_enter`/`plan_exit`/`question` resolve to ask (user can approve) in the decision path where the ruleset path implies the build matrix verdicts; the error is silently dropped in both sites. — fix: mirror policy.go's fallback — retry `LoadBuiltins("build", dataDir)` on unknown-agent error (or centralize the fallback in one helper used by both paths). — contract-risk: none
- [error-4] P2 internal/session/engine.go:803 — `finishRound` silently returns on `UpdateMessage` error (:803-805), skipping the final `message.updated` publish too (TUI keeps a cost-less/incomplete final state); same swallow-and-discard pattern at `saveDelta`/`startPart` (:648, :664 `return` on UpsertPart error), `finalizePart` (:681 `_ =`), `saveSynthetic` (:826 `_ =`), `saveToolPart` (:1045 `_ =`) — mid-turn DB write failures are dropped with zero diagnosis although the engine holds `e.lg`, so silent data loss (part state, tokens, cost, error notes) is undiagnosable. — fix: log each failed persistence via `e.lg.Errorf`/`Errorln` (nil-guarded), keep the non-fatal control flow. — contract-risk: none
- [error-5] P3 internal/permission/service.go:107 — `decisionFor` discards the `AlwaysRules` DB error (`always, _ :=`): a DB failure silently degrades to "no always rules", re-asking the user for tools they already approved for the session, with no diagnostic. Fail-safe direction, but a swallowed storage error. — fix: log (needs a logger seam) or document the degradation like the config-load one. — contract-risk: none
- [error-6] P3 internal/provider/provider.go:113 — zen catalog load error, `ParseZenCatalog` error, and `zenMeta`'s unmarshal error (zen.go:88) are all silently swallowed: the zen provider can vanish from `/provider` (or, from a malformed-but-parseable catalog missing `opencode.api`, appear with an empty `BaseURL`) with zero diagnostics anywhere (the provider package has no logger; the kido probe documents its fallback contract at kido.go:12-24 but New never documents zen's optional-ness). — fix: document the best-effort contract on `New` (as `FetchKido` does) and/or surface a diagnostic; at minimum guard against empty `BaseURL` in the zen `Info`. — contract-risk: none
- [error-7] P3 internal/provider/provider.go:103 — dead error check: `FetchKido` never returns a non-nil error (every path returns the fallback + nil, by documented design), so `if err != nil { return nil, err }` is unreachable and misleads readers into thinking a kido probe failure can abort startup. — fix: drop the check, or give `FetchKido` a real error surface if probe failures should ever be loud. — contract-risk: none
- [error-8] P3 internal/session/engine.go:267 — every event publish swallows `protocol.MakeEvent` marshal errors silently (engine `publish` :267-269; same pattern in permission `resolve` :283-285 and `publishAsked` :343-345): if a future props type becomes unmarshal-incompatible or has an unencodable field, that entire event stream dies with no log line anywhere. — fix: log via the available logger (engine `lg`) at the publish sites; in `permission.Service` at least document/tolerate the drop. — contract-risk: none
- [error-9] P3 internal/session/engine.go:367 — single-handling-rule pair: the abort `context.Canceled` is logged (`lg.Infof` :367) AND returned via `turnErr` → `onDone`, and retry exhaustion is logged (`lg.Errorf` :613) AND returned the same way; if the `onDone` consumer (server handler, outside this chunk's scope) also logs the turn error, each abort and each exhausted retry produces duplicate log lines. The `onDone(err)` call itself is locked (deviation 28). — fix: verify the consumer; if it logs, drop or downgrade the engine-side logs (abort → Debug). — contract-risk: none
