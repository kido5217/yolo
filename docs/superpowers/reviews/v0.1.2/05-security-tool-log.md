# golang-security — tool+log
Date: 2026-08-21 · chunk: tool+log · source files: 12
## Findings
- [security-1] P1 internal/tool/glob.go:115-147 — glob walks the entire search tree and collects every matching path into `files` before applying the 100-result cap, with no early stop. Upstream bounds the work: ripgrep output is taken with `Stream.take(limit+1)` (packages/core/src/ripgrep.ts), so the walk stops after 101 matches. Here a model call `glob {pattern: "**", path: "/"}` (or any approved external dir / always rule) walks the whole filesystem, retaining every matching absolute path (unbounded memory — GB-scale on broad patterns) for minutes of CPU; on low headroom the OOM killer can take yolo down. Contrast: grep.go:192-195 is correctly bounded with `fs.SkipAll` at the limit. — fix: bound the walk the way grep does — stop the walk / stop collecting once a hard cap (e.g. a few × globLimit) is exceeded, or drop the full-tree sort (upstream does not sort either) and keep insertion order. Keep the 100-result output shape. — contract-risk: behavior
- [security-2] P2 internal/tool/bash.go:83-90 (+ shell.go:84,117-121) — model-supplied `timeout` removes the per-command bound: `bashArgs` accepts `timeout: 0` (argInt allows 0) although its error message says "timeout must be a positive integer" and `Shell.Exec` treats `<= 0` as "no timer", leaving only ctx abort as a stop. Huge values are worse: `time.Duration(n)*time.Millisecond` overflows int64-ns for n around 9.2e12 ms and wraps, so the timer can fire at an arbitrary (sometimes immediate) wrapped instant. Upstream declares `PositiveInt` in the schema, throws on `< 0` (shell.ts execute), and treats 0 as a 100 ms (immediate) timeout. — fix: reject or clamp `timeout <= 0` in bashArgs and clamp to a sane max (e.g. 24 h) before the Duration conversion. — contract-risk: behavior
- [security-3] P2 internal/tool/write.go:119-143 (also edit.go:155 and edit.go:157 via `diffCounts`) — every write/edit computes added/removed with a naive full-DP LCS over all lines: O(len(a)*len(b)) work regardless of how small the change is; port-specific, since upstream uses the JS `diff` package (`createTwoFilesPatch`/`diffLines`, Myers — near-linear for a one-line edit in a large file). A single-line edit of a ~60k-line file is ~3.6e9 DP cells (tens of seconds of blocked engine CPU); ~1e6 lines is ~1e12 (impractical). Model-triggered stall reachable by reading then editing one large file. — fix: use an adaptive Myers line diff, or compute the diff only around the replaced region (editApply already knows it) instead of full-DP LCS. — contract-risk: behavior
- [security-4] P2 internal/log/log.go:44 (and :41) — log file created 0o644 (world-readable after default umask) and parent dir 0o755. Content includes error strings, request paths, and full panic stack traces (server recoverMiddleware); on a multi-user host other local accounts can read session debug detail (CWE-732/312). Skill rule: log files 0600. — fix: `os.OpenFile(l.path, ..., 0o600)` and `os.MkdirAll(..., 0o700)` (or at least 0o750). — contract-risk: none · status: FIXED ad9fc09
- [security-5] P3 internal/log/log.go:62 — `write()` emits `text` unvalidated: embedded newlines/CR/control characters (error strings, HTTP `r.URL.Path` via recoverMiddleware, model/tool text flowing into Errorf) can forge additional log lines (CWE-117 log injection; local file only, low severity). — fix: sanitize before write — replace `\n`, `\r`, and other control runes (or %q the payload). — contract-risk: behavior
## Deferred / Noted (no fix in 0.1.2)
- edit.go `editLocks` sync.Map grows unboundedly (one mutex per distinct path for the process lifetime, never evicted) — mirrors upstream edit.ts module-level `Map<string, Semaphore>` (also never cleaned); per-entry footprint negligible, needs ~1e6 distinct paths to matter.
- write.go has no per-file lock (edit.go does) — faithful: upstream write.ts takes no lock; `os.WriteFile` is O_TRUNC+write so concurrent writers are last-writer-wins, not interleaved corruption.
- Shell inherits the full process environment (`cmd.Env = os.Environ()`, shell.go:219) — API keys resolvable by a model holding bash permission; upstream passes full `process.env` too; inherent to the bash grant, not a port gap.
- Symlink-aware writes: permission is anchored to the logical path (Patterns/External see the given path), while edit/write follow symlinks — a symlink inside the project can target a file outside; upstream edit/write behave the same (logical path, no realpath before write) — faithful, noted.
- `base64 -w0` in the marker (shell.go:104) is GNU-only: on BSD/macOS base64 the cwd marker is undecodable, `s.cwd` stops updating, and respawn falls back to `Dir` — pinned plan protocol (line 2739), robustness not security.
- Persistent-shell stdin is shared: a command that reads stdin (e.g. `cat`) swallows later markers/lines and corrupts shell state until the process dies; self-inflicted by the model (threat model), respawn recovers.
- readLoop/readLines have no per-line memory cap: a single multi-MB no-newline output line is buffered whole (output buf itself is capped at 10MB, shell.go:24; read.go:239 accumulates the full line before the 2000-char cut) — upstream lines() is stream-based but splitLines has the same single-line exposure.
- `miss()` (read.go:346-365) lists up to 3 sibling paths for a missing file — sibling names disclosed even when only the missing file's own permission rule was granted; port of upstream `miss` behavior.
- bash permission resource is the first whitespace token (+ ` *`) — pinned v1 simplification of upstream's tree-sitter scan (bash.go:42-45 comment); forms like env-assignment prefixes are not individually gated; plan-pinned, not a finding.
- shell.go:46 `limits` field is set by NewShell but never used (bash tool truncates with `env.Limits.def()` itself) — dead field.
- glob/grep skip all dot-entries, so `.git` (can hold embedded credentials in remote URLs) is never enumerated by these tools — stricter than upstream's `.git`-only exclusion; good.
