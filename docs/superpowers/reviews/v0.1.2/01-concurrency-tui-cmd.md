# golang-concurrency — tui-program+cmd
Date: 2026-08-20 · chunk: tui-program+cmd · source files: 13
## Findings
- [concurrency-1] P2 main.go:278 — Logger double-Close on every exit path that drains: `drain()` calls `deps.Log.Close()` (main.go:278) and every caller also runs `defer closeDB()`, whose `closeDB` (main.go:120-123) calls `lob.Close()` on the same `*log.Logger` (deps.Log is lob, main.go:131). Affected paths: tuiMode success (main.go:257), tuiMode listen error (main.go:227), tuiMode session-check error (main.go:249), serve signal exit (main.go:314), serve listen error (main.go:304). Impact: Close runs exactly twice per exit; if `internal/log` Close is a channel-writer close (typical) the second close panics and replaces the intended exit code with a crash at process exit — an error path (bad session id, port in use) becomes a stack trace. — fix: close the logger in exactly one place — either drop `lob.Close()` from `drain()` and let `closeDB` own it (buildDeps pre-openDB failure already closes via `fail`), or drop it from `closeDB` and close in drain; verify `log.Close` idempotency either way (internal/log is outside this chunk's scope) — contract-risk: behavior
- [concurrency-2] P2 app.go:290 — No context timeout on `createSessionCmd` (app.go:290: `a.CreateSession(context.Background(), "")`) and on both `hydrateCmd` branches (app.go:224 GetSession/ListCommands/ListMessages; app.go:241 ListSessions/ListCommands/GetConfig), while every other outbound call in this chunk uses a 5s `context.WithTimeout` (app.go:439, 491, 627, 672, 679, 724; permission.go:68; main.go:240). Impact: a hung POST /session or hydrate GET blocks its cmd goroutine forever (bubbletea v2 deliberately leaks long-running cmd goroutines — verified in tea.go `handleCommands`: "we'll have to leak the goroutine until Cmd returns") and freezes the TUI in "loading…" with no recovery; realistic in-process trigger is SQLite write-lock serialization behind a long engine turn. — fix: wrap both in `context.WithTimeout(..., 5*time.Second)` + `defer cancel()` to match the established convention — contract-risk: behavior
- [concurrency-3] P3 client.go:45 — SSE backoff `d := time.Second << uint(n)` overflows int64 for n ≥ 34 (1_000_000_000 << 34 > MaxInt64 → negative); the 30s cap only clamps positive values, so `c.backoff(n)` returns a negative duration and `time.After(<0)` at event.go:33 fires immediately — after ~15 min of continuous reconnect failure the backoff degenerates into a tight reconnect loop. Unreachable in the in-process deployment (local server never down) but the wire-contract client is wrong beyond 34 consecutive failures. — fix: clamp n (e.g. `if n > 5 { n = 5 }`) before the shift, or use a math-safe exponential — contract-risk: behavior
- [concurrency-4] P3 app.go:134 — `store.Conn` ("● live" footer, footer.go:82-86) can only be falsified by `connLostMsg`, which fires only when the Events channel closes — i.e. only at program exit (Close → ctx done → `defer close(ch)`, event.go:22-37). Transient SSE drops are absorbed silently by the client's internal backoff-reconnect loop (event.go:25-36, comment app.go:176-178) with no message to the app, so the footer renders "● live" throughout the outage window. Display state contradicts reality in exactly the case the indicator exists for; near-theoretical in-process, real for a remote server. — fix: surface connection state transitions to the app (e.g. client pushes a connUp/connDown msg into the same EventMsg stream or a state channel) so Conn flips off during backoff — contract-risk: render
- [concurrency-5] P3 main.go:234 — Signal handling gaps on both server modes: (a) tuiMode registers `signal.Notify(stop, SIGINT, SIGTERM)` but nothing ever reads `stop`; a signal arriving in the pre-Run window (server start → `tea.Run`, up to 5s during the resume check) is buffered and dropped — the process does not terminate and the user lands in the TUI with their termination request silently lost (recovered only by exiting the TUI or a second SIGTERM, which bubbletea maps to clean exit 0); (b) serve consumes one signal (`sig := <-stop`, main.go:312) and the cap-1 channel drops any repeat SIGTERM during the ≤5s drain — no force-kill path. — fix: (a) select on `stop` alongside program start so a pre-Run signal aborts startup (return 130/143) instead of opening the TUI; (b) on serve, re-arming or accepting the second signal as force-exit — contract-risk: behavior
## Deferred / Noted (no fix in 0.1.2)
- `time.After` per reconnect iteration (event.go:33) — skill principle #8 target, but the loop only spins on disconnects (minutes apart at steady state), not a hot loop; acceptable.
- No join mechanism for the client goroutines: `App.Close()` (app.go:97) cancels the ctx but never waits for the Events reader or the blocked `eventPump` cmd goroutine to exit. Bounded by process exit in the single-binary lifecycle; bubbletea v2 itself documents leaking in-flight cmd goroutines at shutdown (tea.go `handleCommands`). A `Wait()` on Client/App would be the structured-concurrency improvement.
- Verified, not findings: eventPump is at most one goroutine outstanding (re-armed per EventMsg, app.go:132; terminates per event); batch cmds run in goroutines so a blocking pump cannot freeze the event loop (v2.0.8 tea.go:841-842 `go p.execBatchMsg`); `client.Send` post-termination is a no-op (v2.0.8 tea.go `Send` select on ctx.Done) so no blocked send after exit; Client struct is immutable after construction and all methods stateless — `do`/`Events` safe for concurrent use (http.Client-safe).
