- [troubleshoot-1] P1 internal/session/engine.go:853 — overflowRe `(?i)(context|tokens?|too long|exceeds)` over-matches: any non-transient provider error whose message merely contains one of those words (401 "Invalid ... token", 403 "Free usage ... exceeded", 413 body-size) is silently reclassified as context overflow — isOverflowError at engine.go:608 and :725 — so the turn ends idle with turnErr==nil (onDone(nil)) and a synthetic note "context overflow: model context N exceeded by input 0 tokens; the turn stopped. Upstream (checked /tmp/opencode-upstream) uses ~27 narrow patterns plus explicit exclusions (rate limit / throttling / too many requests) plus status 413 / `context_length_exceeded` code (packages/llm/src/provider-error.ts:36, packages/opencode/src/provider/error.ts:168). — fix: port the narrow pattern list + exclusions (or require 400/413 status + specific pattern); never return `false, nil` for a misclassified error — surface the original error at the boundary. — contract-risk: behavior
- [troubleshoot-2] P1 internal/session/engine.go:54 — Deps.Log is documented `nil = no-op`, but every diagnostic call site dereferences the pointer directly (engine.go:270, :764, :655, :672, :689, :816, :839, :1060). An Engine built without Log (the harness does exactly this — engine_test.go:134-154 wires no Log) panics in the turn goroutine on the first persistence/marshal error (disk-full/IO hiccup on the per-delta UpsertPart path), and the turn goroutine has no recover, so the panic takes down the whole process. Not triggered in tests because no test forces a DB error mid-turn with lg==nil (full session suite -race green) — latent. — fix: default a no-op *log.Logger in New when d.Log == nil (or make all methods nil-receiver-safe and say so); verify whether cmd/yolo wires a real logger — if production also passes nil this is a live P1 crash path, else contract violation only. — contract-risk: behavior
- [troubleshoot-3] P2 internal/session/engine.go:758 — text/reasoning part re-finalization and ID reuse across tool parts in one round: finalizePart at the first tool part (engine.go:758-759) publishes a final message.part.updated with end time; a later text/reasoning delta in the same stream reopens the SAME part id (engine.go:742-745: `textSt.id == ""` false → saveDelta on the finalized state, a delta event for an already-finalized part, DB row transiently loses time.end); then each subsequent tool part and the EOF path (engine.go:772-773) re-finalize it. Net: tool rounds emit ≥2 final part.updated frames per text part (end = round end, i.e. includes tool-execution time) and text blocks after tool calls merge into the first part id. Upstream (checked processor.ts:486-532) creates a NEW part id per text block (text-start) and finalizes once (text-end resets currentText). Rendering stays consistent (store replaces on part.updated; no DB corruption), so this is a wire + transcript-structure fidelity gap; the deviation-21 "exactly one final part.updated" pin is honored only for pure-text rounds (the one counting test, engine_test.go:459-470, is text-only and no golden covers a tool-round SSE stream). — fix: on a tool part, mark textSt/reasonSt ended (keep id for no further saves) and clear id so the next segment starts a fresh part; skip the EOF finalize when already ended. — contract-risk: wire

Upstream has no such shared mutable service (rules evaluated from the per-prompt config snapshot). Escalate to P1 if the perm chunk confirms decisionFor consumes the stored state. — fix: pass dataDir+rules as parameters to Ask/decisionFor like the EvaluateRules calls do; drop the Set* per-turn writes. — contract-risk: behavior
